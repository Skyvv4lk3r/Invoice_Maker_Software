01 Owner workflows and system scope

The owner operates the offline desktop app; external recipients receive exported files and have no direct database access.

Full-size SVG · Editable PlantUML
  1. Confirmed scope: sales invoices for goods and services; numeric-only annual numbering; automatic totals and words; PDF/DOCX; inclusive date-range view and sharing. Supporting master, payment and backup features remain the proposed baseline.
  2. Template configuration is now a first-class workflow. The initial release uses approved A4 PDF/DOCX layout pairs with editable branding and optional content; arbitrary executable templates and a full canvas designer are outside version 1.
  3. Sharing prepares files and reveals their location. The owner attaches them in email or WhatsApp. Purchase capture, automatic message delivery, cloud links and multi-computer access are future modules.

02 Frontend, backend and dependency direction

The desktop frontend and backend are separate Python packages, connected by explicit contracts rather than concrete implementation imports.

Full-size SVG · Editable PlantUML
  1. The UI imports application.contracts, not handlers, domain aggregates, SQLAlchemy models or renderer libraries. DTOs contain plain IDs, dates, integer paise, tuples and status/error codes; no QObject, QWidget, Session or library-specific objects cross the boundary.
  2. Application handlers and domain rules never import presentation. Domain and contract packages use the standard library only. Only bootstrap knows concrete frontend, handlers and infrastructure adapters; no global service locator is exposed to views.
  3. This is an in-process modular monolith, not a network API. Logical separation is sufficient for version 1. A future HTTP/IPC adapter may implement the same public contracts, but needs explicit serialization, authentication and failure semantics.

03 Passive views, view models and asynchronous calls

Widgets manage display and input. View models translate user actions into backend requests and map result DTOs to UI state.

Full-size SVG · Editable PlantUML
  1. A view model copies form values into an immutable request before dispatch. QtTaskBridge owns QThreadPool integration and queues results back to the GUI thread. Each backend operation creates its own unit of work; no database connection is shared through a widget.
  2. Client-side checks improve interaction, while backend validation remains authoritative. Live totals come from IInvoiceQueries.calculateDraft; the frontend does not duplicate tax or amount-in-words formulas. Stale asynchronous results are ignored by request ID.
  3. The list view uses paged queries. Export receives the filter itself, not the visible row collection. TemplateSettingsViewModel also receives template queries and preview ports; the diagram shows its command dependency to keep this view readable.

04 Public invoice contracts and plain DTOs

Inbound ports are the stable frontend/backend boundary. Implementations can be called by Qt, a headless test or a later transport adapter.

Full-size SVG · Editable PlantUML
  1. Use frozen dataclasses and typing.Protocol for these contracts. Signatures abbreviate Result[T, ApplicationErrorDTO]; every method has typed success or failure. DTOs are snapshots of data, never mutable domain or ORM objects.
  2. InvoiceIssueService implements all three port methods and delegates to separate IssueInvoiceHandler, CorrectInvoiceHandler and CancelInvoiceHandler objects. A request ID plus payload hash makes issuance idempotent; reusing a key with different input is a conflict. expectedRevision detects stale edits. Invoice number is null for drafts and a positive integer after issuance; the internal UUID remains the durable identity across financial years.
  3. Errors include VALIDATION, CONFLICT, NOT_FOUND, UNSUPPORTED_TAX_TREATMENT, TEMPLATE_UNAVAILABLE, STORAGE_FAILURE and RECOVERY_REQUIRED. The UI translates codes to messages; backend exceptions and SQL traces remain in local diagnostics.

05 Template, preview, export and job contracts

The frontend requests capabilities. It does not choose renderer classes, pass database sessions or read internal artifact paths.

Full-size SVG · Editable PlantUML
  1. Additional cohesive ports cover IMasterDataCommands/Queries, IPaymentCommands/Queries and IBackupCommands/Queries. Capability groups are injected separately; a screen receives only the capabilities it uses.
  2. Preview requests bind both invoice revision and template candidate hash. A later edit cannot quietly change the content of an already-running preview. UI polling of IJobQueries or QtTaskBridge signals uses plain JobStatusDTO objects.
  3. Artifact IDs are resolved by backend services. Export/save/open operations validate selected destinations. Windows handoff does not mean sent or delivered; direct email or messaging would require a separate delivery contract.

06 Invoice identity and immutable financial facts

The sales aggregate contains financial facts and lifecycle rules. It has no knowledge of Qt widgets, DOCX files or PDF layout.

Full-size SVG · Editable PlantUML
  1. Drafts can be empty; issuance requires at least one valid line. The displayed invoice number is only 1, 2, 3, etc. Financial year is internal metadata, derived from invoice date, with separate sequences beginning at 1.
  2. FrozenLine is a distinct value object, not a pointer back to mutable draft or catalogue data. Issued party, line and total snapshots survive later changes to customer details, prices or tax settings.
  3. Document appearance is pinned by a separate RenderBinding (view 10). SalesInvoice and InvoiceSnapshot do not depend on TemplateVersion, ReportLab or docxtpl. Snapshot values include approved terms and payment details; templates cannot override financial facts.

07 Calculation policy and formatting responsibilities

There is one authoritative calculation path. The UI and all document formats consume its results.

Full-size SVG · Editable PlantUML
  1. InvoiceDocumentMapper consumes frozen financial facts. It has no dependency on InvoiceCalculator and cannot invoke tax calculations. Sharing a value-object schema does not couple document layout to the calculation implementation.
  2. Use Decimal for quantity, prices, discounts, rates and intermediate values; integer paise for settled amounts. Configure and test rounding explicitly. Convert the final rounded amount, including paise, to words.
  3. Tax policy uses explicit supply context and approved treatment. It must not infer every service or special transaction solely from two state codes. Unsupported treatments return validation errors; a template never chooses a tax rate.

08 Masters, payments, adjustments and audit history

Reusable masters speed entry. Payments, tax adjustments, document files and audit history remain separate concepts.

Full-size SVG · Editable PlantUML
  1. Payment status is derived from receipts, reversals and allocated adjustments; it is not the invoice lifecycle. A paid invoice does not disappear from the date-range sales register.
  2. Credit/debit notes are separate issued documents with their own numeric sequence per financial year and document kind. They may reference older invoices and are selected by note date in the adjustment register.
  3. Audit history is append-only through application contracts. This is an audit trail, not a claim of tamper-proof storage against a Windows administrator.

09 Template catalogue, revisions and appearance

Template editing is independent of invoice calculation. Publishing produces a versioned PDF/DOCX bundle with validated appearance settings.

Full-size SVG · Editable PlantUML
  1. Version 1 offers approved layouts and constrained appearance settings. PDF layout descriptors and DOCX files are paired assets. Application UI themes and invoice appearance are separate settings; a dark application theme does not recolour printed invoices.
  2. Validation is tied to the exact candidate hash. Any edit invalidates the old report. Publishing requires required-field checks, both format samples and recorded visual review; python-docx/docxtpl generates DOCX but does not itself verify Word pagination.
  3. TemplateVersion content is immutable after publication; retirement is availability metadata only. Existing bindings may still use retired versions. Changing the default affects new bindings and never rewrites historical documents.

10 Financial facts, template binding and document model

A binding freezes which layout, branding and rendering versions are used for a particular financial snapshot.

Full-size SVG · Editable PlantUML
  1. The binding fingerprint covers snapshot content, template bundle, branding assets, locale, document-model schema and renderer-set version. Artifact uniqueness uses binding ID + format + concrete renderer version, so a logo or template change cannot overwrite an old file.
  2. Header, buyer, invoice metadata, item rows, totals and footer are explicit template sections. Invoice number, GST amounts and amount in words are supplied values. The mapper formats these values; it does not calculate or alter them.
  3. Preview uses a distinct PreviewBinding with captured draft facts, draft revision and candidate hash; it has no issued number and always carries a DRAFT watermark. A new appearance for an issued invoice creates a labelled derived copy rather than replacing the canonical issued artifact.

11 PDF and Word adapters behind one render contract

Both adapters accept the same neutral document model. Only the adapters import ReportLab, docxtpl or python-docx.

Full-size SVG · Editable PlantUML
  1. PDF uses approved ReportLab layouts; DOCX uses approved .docx placeholders and item-row loops through docxtpl. Use strict missing-field validation and XML escaping. Approved tags substitute fields, repeat rows and select optional blocks; templates do not contain financial formulas. Arbitrary executable uploads are outside the initial release.
  2. Renderers preserve data and return bytes plus format metadata or a typed rendering error. They never allocate invoice numbers, write business records, show dialogs or perform network calls. Font, logo and signature assets are resolved before rendering.
  3. PDF and Word must agree on facts, totals and branding. They are not promised identical pagination or pixels. The canonical PDF is archived; historical layout reproducibility requires retained assets and renderer versions, not only a template name.

12 Atomic issuance using segregated persistence ports

A work-scope factory supplies narrow repository interfaces participating in one transaction; repositories do not commit independently.

Full-size SVG · Editable PlantUML
  1. This replaces the earlier IIssuanceRecordWriter grouping. Snapshot storage, audit append and job enqueue have separate interfaces. IssuanceWorkScope is an immutable dependency bundle, not a service locator or a class containing business logic.
  2. SQLAlchemyUnitOfWork and SQLAlchemy repositories are infrastructure adapters over SQLite. Every repository in a scope uses the same session/connection. Verify emitted transaction SQL actually takes the intended SQLite write lock; ORM defaults alone are not the numbering guarantee.
  3. The work scope also supplies an idempotency-receipt repository and read-only template/default lookup; these are omitted from the picture to keep it legible. All issued rows, binding, counter, audit, job and request receipt commit or roll back together.

13 Issue once while pinning the exact template version

The transaction fixes both legal facts and document appearance. Rendering is deferred to a durable job after issuance.

Full-size SVG · Editable PlantUML
  1. Number allocation uses the scope (firm, financial year, document kind), with database uniqueness and a transaction. The first number in a new financial year is 1. No clock-triggered reset job or MAX(number)+1 is used.
  2. Validation is authoritative in the backend. Issued numbers/dates are not ordinary editable fields. Template selection inside the issuance snapshot prevents an active-template change racing with issuance.
  3. The diagram shows the successful commit path. Any database failure rolls back if still active; after an uncertain response, look up the same request ID before retry. PDF failure never reissues the invoice. GST/IRP applicability must be resolved before production release.

Sequence diagram

14 Frontend/backend interaction without shared UI objects

The backend knows nothing about the window that invoked it; the frontend knows nothing about the repository or renderer implementation.

Full-size SVG · Editable PlantUML
  1. Only QtTaskBridge and view/view-model code use Qt signals, QThreadPool or widget types. The handler is a normal Python object and can execute in a headless test with no QApplication.
  2. Frontend cancellation of waiting does not undo a committed invoice. The UI reconciles command results by request ID. Safe job cancellation is a separate backend capability and applies only at defined checkpoints.
  3. Live calculation uses the same public boundary. A small local calculation can execute synchronously when measured safe; all database/file-heavy operations use the bridge so the GUI event loop remains responsive.

15 Editing, validating and publishing a template

Publishing creates a validated immutable bundle; activating it changes which version is selected for future invoice issuance.

Full-size SVG · Editable PlantUML
  1. Template validation checks required invoice fields, compatible model schema, approved fonts and assets, placeholder completeness, long text and multipage item tables. It does not calculate GST or change invoice values.
  2. PDF and DOCX samples must be inspected. A DOCX generation library is not a Word layout engine, so visual approval is recorded explicitly. Changing a candidate after validation or review invalidates that evidence.
  3. Store immutable assets successfully before committing references to a published bundle. A failed metadata transaction may leave removable unreferenced assets, but must not publish a version pointing to missing files. Publishing and activation are idempotent audited commands.

16 Preview through the actual document renderer

Preview follows the same mapper and format adapter as final output, with explicit draft identity and captured template inputs.

Full-size SVG · Editable PlantUML
  1. A preview is not a screenshot of the Qt form. PDF preview opens the generated PDF; DOCX preview opens the generated Word file in the chosen viewer. Embedded preview can be added behind a presentation adapter later.
  2. PreviewBinding has captured draft facts, revision, candidate hash and branding but no issued invoice number. Its artifacts have separate retention and keys, carry a DRAFT watermark and never replace canonical issued documents.
  3. Background workers update job records, not view models. The UI obtains plain status DTOs through IJobQueries. If either the draft or template changes, a completed preview is marked stale and can be regenerated.

17 Recoverable rendering through backend-owned ports

The backend publishes durable artifacts and job state. The GUI observes results through public queries; the worker has no GUI reference.

Full-size SVG · Editable PlantUML
  1. A job loads the financial snapshot, published template bundle and branding snapshot through RenderBinding. The mapper prepares a neutral model and the renderer only formats it; neither changes financial facts or invoice state.
  2. The unique artifact key includes binding ID, format and renderer version. A crash after file publication but before database registration is repaired by verifying the existing artifact and completing the same job.
  3. File publication and SQLite commit are separate atomic boundaries. Durable jobs bridge them. UI polling or presentation-adapter notifications obtain JobStatusDTO through IJobQueries; there are no worker-to-widget calls.

18 Date-range export with frozen members and bindings

The package matches a frozen selection, including records on every result page and across multiple financial years.

Full-size SVG · Editable PlantUML
  1. Capture every matching record across all result pages using inclusive invoice dates. Export members pin snapshot/binding IDs, selected status, revision and calculated register values. Drafts require an explicit option and a DRAFT label; paid and unpaid issued invoices are both included.
  2. Cancelled originals remain preserved and identifiable in a separate cancellation register. Credit/debit notes are listed by note date and may reference older invoices. Captured manifests make totals and generated documents consistent despite later edits.
  3. Separate financial-year folders prevent filename collisions while the printed invoice number stays numeric only. The package contains PDFs, optional DOCX, invoice/line registers and GST summaries. Handoff is not an automated GST filing, upload schema certification or delivery receipt.

19 Invoice lifecycle independent of payment and rendering

Draft editing remains convenient. Issued records preserve traceable history and use explicit correction actions.

Full-size SVG · Editable PlantUML
  1. Deletion is an application operation on drafts, represented by a tombstone rather than silent erasure. Issued invoices cannot be physically deleted through the UI.
  2. A clerical revision must pass a CorrectionPolicy and keep the original snapshot and artifact. Changes to amount, tax, invoice date across years or identity are not generic edits.
  3. Cancellation rules depend on document treatment and filing state; they require a reason and linked settlement handling. External GST/IRP deadlines or permissions must be added if applicable; this lifecycle is not a substitute for those rules.

20 Template lifecycle and immutable publication

Candidate changes are editable; published content is immutable, and default selection is separate from version identity.

Full-size SVG · Editable PlantUML
  1. A candidate cannot be published using a validation report for another hash. Review approval is tied to both PDF and DOCX sample artifacts generated from that candidate.
  2. Retiring a version prevents new selection while preserving existing documents. The active default cannot be retired until a valid replacement is selected or issuance is explicitly blocked.
  3. Referenced versions, fonts, logos and source layouts are not hard-deleted. A new logo, layout or font selection creates a new version/branding snapshot for new bindings; historical artifacts remain accessible.

21 Job lifecycle, retries and handoff semantics

The job lifecycle applies to rendering and export. Backup tasks use the same progress/error concepts but maintain their own backup records.

Full-size SVG · Editable PlantUML
  1. User cancellation of an export never cancels an issued invoice. A pending canonical PDF job is retried rather than silently discarded.
  2. Progress and error signals are queued back to the GUI thread. Each worker uses its own database connection; widgets are manipulated only on the main thread.
  3. Disk-full, permission and template errors are distinct retryable outcomes. Logs avoid full customer details and document content unless explicitly needed for an audited local diagnostic.

22 Invoice persistence and annual numbering constraints

Storage rows are infrastructure models mapped to domain aggregates; the frontend never receives a database row or SQLAlchemy object.

Full-size SVG · Editable PlantUML
  1. Enforce UNIQUE(firm_id, fy_start, invoice_no) WHERE invoice_no IS NOT NULL, positive integer numbers no longer than 16 digits, UNIQUE(invoice_id, revision), and a unique request receipt. Credit/debit note tables use their own document-kind scopes.
  2. Enable foreign keys on each connection and index invoice-date/status/customer queries. Use ISO local dates for invoices, UTC timestamps for events, Decimal strings for exact inputs and integer paise for settled money. Reject non-finite numbers and invalid quantities.
  3. SQLAlchemyUnitOfWork performs explicit transactions. Alembic versioned migrations run after a verified pre-upgrade backup. Repository mappers detach domain objects from ORM sessions; optimistic row versions prevent overwriting another edit.

23 Template, branding and document persistence

Templates and branding are durable versioned records, not a mutable file path stored on each invoice.

Full-size SVG · Editable PlantUML
  1. Enforce UNIQUE(family_id, version) and UNIQUE(binding_id, format, renderer_version). Template/branding asset link tables preserve referenced hashes. Active template selection is stored separately per firm and document kind.
  2. Additional tables store template_validation_report, template_review_receipt, default_template_selection and preview_binding. A draft preview uses preview_artifact storage with its own lifecycle; nullable polymorphic references must not weaken issued-artifact foreign keys.
  3. Keep template bundles, font assets, logos and canonical documents in the backup manifest. Only unreferenced temporary assets can be cleaned automatically; retirement is not deletion. Filesystem publication is atomic, then metadata references are committed.

Class diagram with table stereotypes

24 Export manifests, jobs, payments and audit records

Operational state is separate from invoice identity and template versions. A completed export is a frozen record of what was prepared.

Full-size SVG · Editable PlantUML
  1. Export-member document references are logical references in this view. Implementation uses typed membership tables/foreign keys for sales, adjustments and draft previews, or a checked common document-snapshot index; unchecked polymorphic IDs are not acceptable.
  2. Jobs use unique idempotency keys, bounded retries and expiring leases. Audit records capture backend mutations and actor/correlation information. An append-only application interface is not a claim of resistance to local administrator tampering.
  3. Payment status derives from receipts, reversals and allocated credit/debit notes. Track both amount outstanding and any customer credit/refund balance rather than discarding negative net balances. Payments do not change invoice date or tax-register inclusion.

Activity diagram

25 Consistent backup including every template dependency

A recoverable backup contains the database plus every referenced document, template and asset, not just an isolated .db file.

Full-size SVG · Editable PlantUML
  1. Pause new writes and drain active workers through a maintenance gate while taking the database snapshot and copying referenced assets. Back up invoice/adjustment records, audit, template versions, branding, fonts, document artifacts, settings and restore metadata together.
  2. Use SQLite backup facilities and maintained authenticated encryption with a user-held recovery mechanism. Verify hashes and integrity before marking success. A key protected only for one Windows installation is insufficient for recovery on another computer.
  3. Keep multiple dated generations. Copy only completed encrypted archives to the configured cloud-synced folder or external drive. A completed local copy into a sync folder is not proof of cloud upload. Never cloud-sync the active database.

Activity diagram

26 Restore with version integrity and numbering reconciliation

Restoring data and resuming invoice issuance are separate operations because a backup cannot reveal invoices issued after it was created.

Full-size SVG · Editable PlantUML
  1. No blind overwrite of a live database, WAL file or artifact directory. A staged dataset is verified first; a recoverable generation-switch manifest makes an interrupted restore diagnosable on next startup.
  2. A restore reconciliation checks each financial-year/document-kind counter against evidence of all later issued numbers. If evidence is incomplete, issuance remains blocked; a restored counter alone is not sufficient.
  3. Backup key recovery, cross-machine restore, invalid archives, interrupted activation and schema migration are explicit acceptance tests. Logs must not store encryption secrets.

Deployment diagram

27 Runtime deployment with separate frontend and backend packages

Core invoice operations are local and offline. Internet access is needed only for external messaging or cloud backup sync.

Full-size SVG · Editable PlantUML
  1. Version 1 assumes one principal workstation. The installer and updates keep application binaries separate from user data; upgrades take a backup and run versioned migrations.
  2. SQLite is not shared directly between multiple computers. A later multi-computer version introduces an application service and centrally managed database behind repository interfaces.
  3. Windows permissions and device encryption protect local storage at the operating-system boundary. SQLite is not automatically encrypted by adding an app password. No public cloud link service or automatic message sender is deployed in version 1.

28 Purchase expansion through independent module contracts

Purchase capture becomes a separate module with shared export and value-object contracts, not a subclass forced to behave like an issued sales invoice.

Full-size SVG · Editable PlantUML
  1. A purchase retains the supplier-issued invoice number, which may contain letters and symbols. It does not consume the firm's numeric sales sequence.
  2. A minimal InvoiceBase would weaken lifecycle and numbering rules. Separate aggregates preserve valid contracts while shared register adapters permit combined viewing/export later.
  3. Supplier management, purchase validation, input-tax-credit review and reconciliation with GST records are explicitly future scope. The current sales app is not a complete accounting or GST-return filing system.
